## Follow-up trade regression — cancellation spam bypass

A second source review found that `Trade.disconnect` served both user-triggered Cancel and PlayerRemoving. The original expiry patch cleared `lastInvite` inside this shared function, allowing Invite → Cancel → Invite to bypass the three-second notification throttle. The follow-up splits the lifecycle: Cancel only clears pending trades, while `Trade.leave` removes the sender throttle **only on actual player removal**. A headless regression now verifies that cancel-and-reinvite cannot send a second notification before cooldown. Studio multiplayer verification remains pending.

## Additional gameplay repair — session time accuracy

- **Confirmed P1:** `Data.start` formerly granted `Seconds+=60` to every loaded profile on a shared server-wide 60-second loop. A new arrival at the 59-second mark could receive a full minute for one second of play; departure before the next tick lost elapsed progress.
- **Implemented follow-up:** `PlaytimeClock.advance` calculates whole monotonic elapsed seconds with fractional carry for each session. Loading starts that player's own checkpoint; periodic savings, PlayerRemoving leaderboards, unload saves and server shutdown flush actual time once without duplicate credit. Tests cover staggered joins, early leave, uneven intervals, duplicate tick and invalid timestamps.
- **Still needed:** private-published reconnect tests and a live two-client leaderboard minute boundary test, including shutdown under write throttling. The new pure-clock assertions cannot prove Roblox lifetime or DataStore persistence.

## Second-pass re-audit: multi-client trade state (2026-11-14)

- **P1 source finding:** the previous expiry/throttle implementation still allowed one sender to queue a pending invitation to Bob and, three seconds later, another to Cara. A first trade could end while the second invitation was still valid. That invitation represented stale consent from the previous idle state and could unexpectedly open a new session. **Fix:** allow only one outgoing invitation at a time and expose `pendingTo` to the Trade screen, including an explicit Cancel button.
- **P1 source finding:** accepting a trade can call the durable settlement adapter, which yields for persisted writes. While it yields, the old `Trade.action` had no per-session finalization flag; concurrent Cancel, Offer and Accept calls could mutate or clear the same consent state. **Fix:** enter a session-wide `settling` lock before calling the adapter, reject offer/cancel/accept mutations until it returns, and release the lock on safe failure/exception. Force-cleanup remains available during PlayerRemoving.
- **Test evidence:** extend the existing executable headless invite suite with single-outgoing rules, re-entrant Cancel/Offer/Accept attempts within the settlement callback, exception recovery, and successful state removal. Verify in GitHub PR CI and recheck `main` push CI after merging.
- **Important boundary:** `DurableTrades=false` remains. This is a protocol improvement, not proof of cross-DataStore atomicity under crashes, shutdown races, throttling, or real Roblox multiplayer. Private-published fault injection remains a release requirement.

## Second-pass economy integrity: exact rewards and inventory backpressure

- **P1 source finding:** `Rules.add` caps every stack at one million, but `Economy.buy`, `Economy.craft`, `Rules.gather` and `Adventure.hunt` previously applied economic costs or progression without checking whether the complete reward would fit. A full backpack could make a valid purchase or paid craft silently discard items.
- **Change:** introduce pure `Rules.canAdd` to reject invalid/overflowing known grants. Use it before any shop charge, crafting cost, resource-node depletion and successful wild reward. The free daily wheel keeps its cooldown unclaimed when a selected resource prize cannot fit.
- **P1 source finding:** `Economy.tick` paid worker wages before `Rules.add` silently truncated overflowed materials. The UI previously labeled wage-ready work even when a full warehouse meant no goods would arrive. **Change:** bound payable batches by both shared-wallet wages and inventory headroom, hold storage-blocked minutes up to the existing 60-minute backlog cap, preserve the old unpaid-wage expiry policy, and simulate production in read-only worker status. Explain wage vs storage blocks distinctly in the crew HUD.
- **Validation:** use the new real-Luau `test_reward_capacity` suite, the existing payroll tests, source contracts and the Rojo place build. Must still test extreme inventory, caretaker/farmer mixed crews and genuine server clock interactions in Roblox Studio before treating the system as economy-proof.

## Recommended architecture

Keep the existing **server-authoritative** progression rules. Avoid putting economy outcomes or item probabilities on the client.

1. **Domain layer** (`src/shared`): pure deterministic economy, inventory, pet evolution, trading, combat and progression, each with contract / property-oriented Lune regressions.
2. **Application layer** (`src/server`): action dispatch, input limits, per-player operation serialization, exactly-once receipts where value moves, cooldowns, explicit versioned profile migrations, and safe locks.
3. **Runtime adapters**: DataStore / OrderedDataStore, world interaction, matchmaking, telemetry. Deduplicate and bound asynchronous calls, especially leaderboard lookups and persistent writes.
4. **Presentation layer** (`src/client`): small HUD, onboarding objective, disclosure of costs/probabilities, nonblocking loading/error states, keyboard/gamepad/touch parity.
5. **CI / delivery**: PR-triggered lint, real Luau suites, world generation and packaging, plus a separately recorded **manual Roblox Studio / private-published QA gate**. Source tests are never substitutes for multiplayer and durability tests.

## Suggested implementation waves

- **Wave 1 — reliability:** worker rejoin fairness; invitation expiry, consent and notification throttling; PR validation; then remote read budgets and leaderboard singleflight.
- **Wave 2 — first 10 minutes:** progression analytics, improved first hatch and ranch feedback, creature encyclopedia, inventory sorting and discoverable mobile shortcuts.
- **Wave 3 — creature identity:** validated ability cooldowns, enemy telegraphs, audio and animation approval, role balancing and test encounters.
- **Wave 4 — social and retention:** co-op expedition prototype, moderated social features, 2-party trade recovery qualification, limited seasons and event rewards.
- **Wave 5 — expansion and launch:** multi-biome/planet unlocks, safe teleport, profile migrations, large-scale performance checks, accessibility, localization, support and rollback.

These waves are proposed work, not completed features. Keep public deployment disabled until the release gates are measured and signed off.

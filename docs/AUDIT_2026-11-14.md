## Third-pass persistence invariants — bounded currency and pet IDs

- **P1 source defect:** `Rules.load` accepts saved Coins only at or below 4,000,000,000, but `Economy.sell`, `Economy.claim`, `Economy.wheel`, `Adventure.hunt`, `Rules.gather` and level-up rewards previously incremented Coins without enforcing the same limit. Enough earning within one server session could create an unsaveable balance that hydrates back to the starter value. Centralize `MAX_COINS`, cap passive reward overflow, and **reject loss-making sells/claims/spins** before consuming resources or entitlements.
- **P1 source defect:** pet lookup/hydration validates IDs only up to 10,000,000. `Rules.addPet` previously minted higher IDs, creating pets that cannot be selected or preserved after reload. Paid `Main.Hatch` and `Main.UFO` spent materials before `R.addPet`; `E.tradeUp` removed three pets before checking ID capacity. Reject an exhausted sequence before consuming eggs, crafted items, exchange materials or pets. A daily creature wheel with no remaining valid pet IDs delivers its coin fallback.
- **Acceptance:** real shared-module Luau regression for exact-fit sales, blocked claims, no-loss wheel outcomes, final valid pet ID, never burning trade-up pets, capped passive coin awards and profile hydration. Selene/PR CI and main push CI required. Published DataStore migration/rejoin tests remain pending.

## Third-pass gameplay improvement — hunt outcome and responsiveness

- **Confirmed source-level feedback gap:** `Adventure.hunt` calculated rounds, remaining HP and damage, but `Main.server.lua` only used the boolean/message pair; the UI never received those details. The new `combat` client event conveys the server-authoritative encounter outcome and shows a compact non-modal result card (victory, defeat or blocked backpack).

The domain now checks guaranteed loot capacity **before combat** and marks `outcome="storage_full"`, `turns=0`; the server clears the hunt cooldown on that refusal, while genuine losses still incur recovery cooldown.

PR CI lint/package/static tests are required. Roblox Studio must still verify prompt cooldowns, banner visibility on small phones, combat animations and role feedback in real multiplayer.

## Follow-up trade regression — cancellation spam bypass

A second source review found that `Trade.disconnect` served both user-triggered Cancel and PlayerRemoving. The original expiry patch cleared `lastInvite` inside this shared function, allowing Invite → Cancel → Invite to bypass the three-second notification throttle. The follow-up splits the lifecycle: Cancel only clears pending trades, while `Trade.leave` removes the sender throttle **only on actual player removal**. A headless regression now verifies that cancel-and-reinvite cannot send a second notification before cooldown. Studio multiplayer verification remains pending.

## Additional gameplay repair — session time accuracy

- **Confirmed P1:** `Data.start` formerly granted `Seconds+=60` to every loaded profile on a shared server-wide 60-second loop. A new arrival at the 59-second mark could receive a full minute for one second of play; departure before the next tick lost elapsed progress.
- **Implemented follow-up:** `PlaytimeClock.advance` calculates whole monotonic elapsed seconds with fractional carry for each session. Loading starts that player's own checkpoint; periodic savings, PlayerRemoving leaderboards, unload saves and server shutdown flush actual time once without duplicate credit. Tests cover staggered joins, early leave, uneven intervals, duplicate tick and invalid timestamps.
- **Still needed:** private-published reconnect tests and a live two-client leaderboard minute boundary test, including shutdown under write throttling. The new pure-clock assertions cannot prove Roblox lifetime or DataStore persistence.

## Second-pass re-audit: multi-client trade state (2026-11-14)

- **P1 source finding:** the previous expiry/throttle implementation still allowed one sender to queue a pending invitation to Bob and, three seconds later, another to Cara. A first trade could end while the second invitation was still valid. That invitation represented stale consent from the previous idle state and could unexpectedly open a new session. **Fix:** allow only one outgoing invitation at a time and expose `pendingTo` to the Trade screen, including an explicit Cancel button.
- **P1 source finding:** accepting a trade can call the durable settlement adapter, which yields for persisted writes. While it yields, the old `Trade.action` had no per-session finalization flag; concurrent Cancel, Offer and Accept calls could mutate or clear the same consent state. **Fix:** enter a session-wide `settling` lock before calling the adapter, reject offer/cancel/accept mutations until it returns, and release the lock on safe failure/exception. Force-cleanup remains available during PlayerRemoving.
- **Test evidence:** extend the existing executable headless invite suite with single-outgoing rules, re-entrant Cancel/Offer/Accept attempts within the settlement callback, exception recovery, and successful state removal. Verify in GitHub PR CI and recheck `main` push CI after merging.
- **Important boundary:** `DurableTrades=false` remains. This is a protocol improvement, not proof of cross-DataStore atomicity under crashes, shutdown races, throttling, or real Roblox multiplayer. Private-published fault injection remains a release requirement.

## Second-pass economy integrity: exact rewards and inventory backpressure

- **P1 source finding:** `Rules.add` caps every stack at one million, but `Economy.buy`, `Economy.craft`, `Rules.gather` and `Adventure.hunt` previously applied economic costs or progression without checking whether the complete reward would fit. A full backpack could make a valid purchase or paid craft silently discard items.
- **Change:** introduce pure `Rules.canAdd` to reject invalid/overflowing known grants. Use it before any shop charge, crafting cost, resource-node depletion and successful wild reward. The free daily wheel keeps its cooldown unclaimed when a selected resource prize cannot fit.
- **P1 source finding:** `Economy.tick` paid worker wages before `Rules.add` silently truncated overflowed materials. The UI previously labeled wage-ready work even when a full warehouse meant no goods would arrive. **Change:** bound payable batches by both shared-wallet wages and inventory headroom, hold storage-blocked minutes up to the existing 60-minute backlog cap, preserve the old unpaid-wage expiry policy, and simulate production in read-only worker status. Explain wage vs storage blocks distinctly in the crew HUD.
- **Validation:** use the new real-Luau `test_reward_capacity` suite, the existing payroll tests, source contracts and the Rojo place build. Must still test extreme inventory, caretaker/farmer mixed crews and genuine server clock interactions in Roblox Studio before treating the system as economy-proof.

## Recommended architecture

Keep the existing **server-authoritative** progression rules. Avoid putting economy outcomes or item probabilities on the client.

1. **Domain layer** (`src/shared`): pure deterministic economy, inventory, pet evolution, trading, combat and progression, each with contract / property-oriented Lune regressions.
2. **Application layer** (`src/server`): action dispatch, input limits, per-player operation serialization, exactly-once receipts where value moves, cooldowns, explicit versioned profile migrations, and safe locks.
3. **Runtime adapters**: DataStore / OrderedDataStore, world interaction, matchmaking, telemetry. Deduplicate and bound asynchronous calls, especially leaderboard lookups and persistent writes.
4. **Presentation layer** (`src/client`): small HUD, onboarding objective, disclosure of costs/probabilities, nonblocking loading/error states, keyboard/gamepad/touch parity.
5. **CI / delivery**: PR-triggered lint, real Luau suites, world generation and packaging, plus a separately recorded **manual Roblox Studio / private-published QA gate**. Source tests are never substitutes for multiplayer and durability tests.

- **Wave 2 — first 10 minutes:** progression analytics, improved first hatch and ranch feedback, creature encyclopedia, inventory sorting and discoverable mobile shortcuts.

These waves are proposed work, not completed features. Keep public deployment disabled until the release gates are measured and signed off.

## Fourth-pass quality-of-life wave — wallet-bounded Sell Max (2026-11-14)

**Observed bottleneck:** `Pages.backpack` only displayed `SELL 5` for each material. The original `Economy.sell` deliberately accepts no more than 100 per call, while the resource stack limit is 1,000,000. Players with accumulated worker production could require hundreds of separate requests, hitting the 200 ms action cooldown and making inventory management slow.

**Implemented:** `Economy.sellMax` computes the exact amount sellable from the player's current server-owned inventory **and** the remaining `Rules.MAX_COINS` wallet headroom. It uses the same authoritative sale and price checks as existing small sales, refusing overflow/invalid IDs/empty stacks before any deduction. `Pages.backpack` adds a concise Sell Max control with exact count and payout, and disables it when no sale is possible. The existing Sell 5 behavior and 100-unit manual API limit remain unchanged.

**Tests:** new real-module Luau `test_sell_max.luau` covers a million-unit stack, partial sale at coin cap, non-divisible wallet room, exact catalogue payout, invalid/empty resource, double-sale refusal, hydration, and compatibility with original `Sell`. CI/Selene/Rojo/static contracts apply. Manual Studio UI/gamepad, latency and published save/load checks remain mandatory.

**Further features not implemented:** one-tap category filters for the backpack, multi-resource sell preview, opt-in confirmation before high-value bulk sales, resource storage upgrade, collection analytics and worker-return ledger. Do not add blind auto-sell or turn on durable trades before recovery qualification.


## Fourth-pass client/server architecture hardening — monotonic state snapshots (2026-11-14)

**Source-observed ordering hazard:** the same client received authoritative profile and trade snapshots through both `Action:InvokeServer` replies and `Update.OnClientEvent`. The previous client applied whichever arrived last, even when an asynchronous earlier request returned after a newer push. Roblox network and yielding data operations make this a plausible stale-UI scenario, especially around multiplayer acceptance, inventory counts, and player progression. Prior automated tests did not guarantee ordering.

**Change:** maintain a per-player, server-generated monotonic snapshot sequence across *both* RPC reply and state-carrying push paths; client `SnapshotOrder.accept` rejects missing, invalid, repeated or older versions before applying the snapshot. Non-state events (pickup popups, world tab links, combat reports) stay independent, so they are not accidentally dropped. The sequence is session-scoped and cleared on player departure, requiring no profile schema/data migration.

**Acceptance evidence:** headless Luau `test_snapshot_order.luau` models delayed RPC, newer server event, duplicate event, malformed sequence and session reset; source contracts guard both transport paths, and PR CI verifies packaging. These tests do not prove real-world network reordering or all Roblox server-to-client race conditions. Live multiplayer QA must validate a trade partner changing offers during delayed requests, UI notifications, respawns, busy action flows, and disconnect/reconnect.

## Fifth-pass findings — pending trade invitation coherence

The trade state machine previously cleared a pending incoming or outgoing invitation on `Cancel` but only notified the party invoking the RPC. The other client could retain a now-invalid invitation or continue displaying “Invitation pending” until an unrelated server push or action. The authoritative fix emits a state refresh and clear explanation to the counterpart on withdrawal or decline, using the existing `send` event path and without changing trade receipt format or the disabled published-trade gate. `test_trade_invites.luau` now verifies both directions, no stale consent, one notification per cancellation, and failure to join withdrawn invitations. Studio two-client UX and latency tests remain pending.
